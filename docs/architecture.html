Adapter — integrations/oss_adapter.py

The only file that changes when real extracts arrive

Hutch's own field names in, four canonical tables out

One declarative mapping per source. It renames columns, converts units, validates every KPI against its physical range, reports what is missing instead of silently filling it, and aggregates to one row per week. Nothing downstream knows or cares which system the data came from — which is why the model does not need to be rewritten to go live.

Model — models/model.json

ROC AUC 0.864 · PR AUC 0.607 · 5-fold CV 0.857 ± 0.008

Logistic regression, 24 weights

Risk is literally the sum of each feature's weighted contribution, so every score decomposes exactly rather than approximately — the console ranks those contributions and shows an agent why the number is what it is. Benchmarked against gradient boosting on identical data: the linear model scores higher (0.864 vs 0.840), so the explainability the challenge requires costs nothing.

No LLM. No neural network.

24 multiplications and one sigmoid per customer. Scoring an entire prepaid base is seconds of CPU and no token bill at all — so there is no inference cost to forecast, and nothing leaves the building to be scored.

Policy — business rules, deliberately not learned

Hutch can change any of this without retraining

Threshold tuned on money, not accuracy

The alert line is the one that loses the least revenue, given that an offer costs real margin and is wasted on anyone who was never leaving. Not the best F1 score — a different question.

threshold = 0.43 · recall 50% · precision 65%

Suppression — flagged is not contacted

A high score means this customer's experience is degrading. It does not mean spend money today. Three rules hold the offer back, all of them relative to the customer's own normal.

travelling — away from their own usual towers
seasonal — the whole base is down
fatigue — contacted in the last 30 days

Cause attribution

The same features name the most likely reason, so the action can match it. A customer with a bad cell gets a repair update, not a discount — a discount does not fix a dropped signal.

network · bill shock · plan too big
plan too small (upsell)
losing interest · competitor offer

Action & interface

Prototype: staysignalbyfalconyx.netlify.app

Offer matched to the cause

One action per cause, each with a named owner and a cost. Network faults route to the RF team as a work order rather than to marketing as a discount.

Message in the customer's language

SMS written in Sinhala, Tamil or English, chosen from the customer's own language field — not translated at send time.

CEM console for agents

Ranked queue, the evidence behind each score, the named tower, and a separate held-back queue so a suppressed customer is visible instead of silently dropped.

Feedback loop. Every contact, every outcome and every suppression reason is written back to the warehouse, so the next retrain learns from what actually worked — and the save rate stops being an assumption and becomes a measurement.
All data in this repository is simulated. No Hutch APIs, credentials, production systems or data were used. Field names and value ranges follow standard telecom KPI definitions so the schema matches a real export; only the adapter changes when real extracts arrive.
Scale. Nightly batch over the full base; the heavy step is one group-by per table. A one-million-subscriber base is a single-machine job, and the model itself is 24 multiplications per customer.
Privacy. No message content, no packet inspection, no location beyond the cell the network already records for billing. The only external input is district-level market data containing no personal information.
